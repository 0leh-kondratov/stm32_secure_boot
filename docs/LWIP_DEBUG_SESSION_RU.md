# Сессия отладки lwip: запуск под GDB и поиск причины сбоя

Один сценарий от включения платы до выяснения, где именно ломается запуск (и практика GDB).

---

## Подготовка

- Плата **NUCLEO-H743ZI2** по USB (ST-Link).
- Два терминала (или вкладки). В одном будет `st-util`, в другом — GDB.

---

## Часть 1. Запуск под отладчиком

### Шаг 1. Терминал 1 — GDB-сервер

```bash
st-util
```

Оставьте окно открытым. Должно быть: `Listening at *:4242...`

---

### Шаг 2. Терминал 2 — сборка и запуск GDB

```bash
cd /path/to/stm32_secure_boot
make lwip
./scripts/gdb_lwip.sh
```

Скрипт подключится к st-util, загрузит образ в плату, сделает reset+halt и поставит breakpoint на `main`. В конце будет приглашение `(gdb)`.

---

### Шаг 3. Первый запуск

В GDB введите:

```
(gdb) c
```

**Что может быть:**

- **Остановились на `main`** — запуск до main прошёл, сбой дальше по коду (или его нет). Можно ставить breakpoint в `StartDefaultTask`, `log_puts` и т.д.
- **Остановились в `UsageFault_Handler`** (или другом fault) — сбой до или вскоре после входа в main. Переходите к **Части 2**.

---

## Часть 2. Попали в UsageFault_Handler — ищем причину

Не выходя из GDB, выполните по порядку.

### 2.1 Узнать причину сбоя (CFSR)

```
(gdb) p/x *(uint32_t*)0xE000ED28
```

Или после пересборки с нашим кодом:

```
(gdb) p/x g_usage_fault_cfsr
```

Смотрите **старшие 16 бит** (UFSR). Типичные значения:

| Значение   | Причина |
|-----------|---------|
| 0x0100    | UNDEFINSTR — неверная/неподдерживаемая инструкция |
| 0x0200    | INVPC — неверный PC при выходе из исключения |
| 0x0400    | INVSTATE — неверное состояние (например, переход в Thumb с нечётного адреса) |
| 0x0800    | UNALIGNED — невыровненный доступ к памяти |
| 0x1000    | DIVBYZERO — деление на ноль |

Запишите значение (например, `0x400`).

---

### 2.2 Узнать адрес сбойной инструкции

В ячейке **по адресу** `$sp+24` лежит **значение** PC (адрес сбойной инструкции). Сначала прочитайте это значение:

```
(gdb) x/xw $sp+24
```

Запомните **выведенное значение** (например `0x08001234`) — это адрес сбойной инструкции. Затем дизассемблируйте **именно его** (не адрес ячейки стека):

```
(gdb) x/i 0x08001234
```

(подставьте свой адрес). Команда `x/i $sp+24` была бы неверной — она дизассемблирует адрес ячейки стека в RAM, а не код по сохранённому PC. GDB покажет инструкцию и, если есть символы, файл и строку. Так вы узнаете **где** произошёл сбой.

**Если значение по `$sp+24` равно 0:** это возврат по адресу 0 — обычно значит, что в таблице векторов для какого‑то IRQ записан 0, и при срабатывании прерывания CPU перешёл по адресу 0 (INVPC). Нужно в startup заполнить слоты IRQ обработчиками (например `Default_Handler`), а для Ethernet (ETH_IRQn = 61) — `ETH_IRQHandler`.

---

### 2.3 Сброс и повторный прогон (без перезапуска GDB)

```
(gdb) monitor reset halt
(gdb) c
```

- Если снова попали в fault — повторите 2.1 и 2.2 (причина и адрес могут обновиться).
- Чтобы сузить место: перед `c` поставьте breakpoint раньше по коду (см. Часть 3).

---

## Часть 3. Сужаем место сбоя (практика GDB)

Цель: понять, до какого места выполнение доходит, а где уже падает.

### Вариант A: Сбой до main

Поставьте точку в самом начале сброса и идите по шагам:

```
(gdb) monitor reset halt
(gdb) break Reset_Handler
(gdb) c
```

Остановитесь в `Reset_Handler`. Дальше:

- **`n`** (next) — шаг по одной инструкции (без входа в функции).
- После нескольких `n` вы дойдёте до `bl ExitRun0Mode`, затем `bl SystemInit`, затем циклы .bss/.data, затем `bl main`. Если сбой случится во время одного из `bl`, значит падение **внутри** этой функции.
- **`s`** (step) — шаг с заходом в функцию. Используйте, когда стоите на `bl ...`, если хотите зайти внутрь.

Полезно:

```
(gdb) info registers pc
(gdb) disas
```

`disas` покажет дизассемблер текущей функции.

### Вариант B: Проверить, доходим ли до main

```
(gdb) monitor reset halt
(gdb) break main
(gdb) c
```

- **Остановились на `main`** — сбой где-то **после** входа в main (или в самой main). Ставьте breakpoint в `log_init`, `log_puts`, `MPU_Config`, `SystemClock_Config` и снова `c`, чтобы найти строку.
- **Снова попали в UsageFault_Handler** — сбой **до** main (startup, ExitRun0Mode, SystemInit или копирование .data/.bss). Тогда используйте Вариант A с `break Reset_Handler`.

### Вариант C: Breakpoint в конкретной функции

Например, проверить, вызывается ли инициализация UART:

```
(gdb) break log_init
(gdb) monitor reset halt
(gdb) c
```

Если остановились на `log_init` — до этого места выполнение доходит. Дальше можно `n` по строкам внутри `log_init` или поставить break в `log_puts` и снова `c`.

## Часть 4. Полезные команды GDB (шпаргалка)

| Команда | Сокращение | Описание |
|---------|------------|----------|
| `continue` | `c` | Выполнять до следующего breakpoint или fault |
| `next` | `n` | Следующая строка (без входа в функции) |
| `step` | `s` | Следующая строка (с заходом в функции) |
| `break <функция>` | `b main` | Точка останова на функции |
| `break <файл>:<строка>` | `b main.c:72` | Точка останова на строке |
| `info breakpoints` | | Список breakpoint'ов |
| `delete 1` | | Удалить breakpoint №1 |
| `print выражение` | `p/x переменная` | Напечатать значение (`x` = hex) |
| `backtrace` | `bt` | Стек вызовов |
| `list` | `l` | Показать исходный код вокруг текущей строки |
| `disas` | | Дизассемблер текущей функции |
| `load` | | Загрузить образ в плату (после пересборки) |
| `monitor reset halt` | | Сброс платы и остановка в начале |
| `quit` | `q` | Выход из GDB |

## Часть 5. После изменения кода

Пересобрали проект:

```bash
make lwip
```

В **том же** GDB (перезапускать не нужно):

```
(gdb) load
(gdb) monitor reset halt
(gdb) c
```

Или поставьте нужные breakpoint'ы и снова `c`.

---

## Итог

1. **Терминал 1:** `st-util`.
2. **Терминал 2:** `make lwip` → `./scripts/gdb_lwip.sh` → `c`.
3. Если попали в **UsageFault_Handler**: смотрите CFSR (`p/x *(uint32_t*)0xE000ED28`), сбойный адрес (`x/xw $sp+24`, затем `x/i <адрес>`).
4. Сужайте место: `break Reset_Handler` или `break main`, затем `monitor reset halt` и `c`; при необходимости шагайте `n`/`s`.
5. GDB не перезапускайте; после `make lwip` делайте в нём `load`, `monitor reset halt`, `c`.

По этому сценарию можно и найти причину проблем с запуском, и потренироваться в использовании GDB.
