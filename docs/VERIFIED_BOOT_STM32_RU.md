# Verified Boot на STM32: база знаний

Документ в духе [3mdeb/verified-boot](https://github.com/3mdeb/verified-boot): единая терминология и ключевые концепции Verified Boot, адаптированные под **STM32** и минимальный загрузчик с проверкой подписи. Цель — не дублировать общую теорию, а дать связку «понятия → наш проект и референсы ST».

**Аудитория:** разработчики встраиваемых систем, OEM, все, кто хочет делать защищённую загрузку на STM32.

**Использование:** образование, проектирование своего secure boot, сравнение с [X-CUBE-SBSFU](https://www.st.com/en/embedded-software/x-cube-sbsfu.html) и [MCUboot](https://docs.mcuboot.com/).

---

## 1. Цепочка доверия на STM32

### 1.1 Root of Trust (RoT) — корень доверия

**RoT** — компонент (железо или код), которому доверяют по умолчанию. Доверие к нему не доказывается: кто его «проверяет», сам становится новым корнем. Компрометация RoT делает бессмысленными все следующие шаги.

На STM32 в роли RoT обычно выступает:

- **Аппаратный bootloader** (системная память, Boot0=1) — закрытая прошивка ST; или  
- **Первый код во Flash** (Boot0=0) — наш загрузчик по адресу `0x08000000`, если мы считаем его доверенным (записан в доверенной среде, при необходимости защищён от перезаписи через WRP).

В этом проекте **RoT = бутлоадер в начале Flash**: он не проверяется другим кодом на крипте, мы полагаемся на то, что его записали корректно и защитили от подмены (опционально — write protection).

### 1.2 Root of Trust for Verification (RTV)

**RTV** — компонент, который **проверяет** следующий образ (целостность и подлинность) **до** передачи ему управления. Цитата по ARM: «неизменяемое место (например boot ROM), которое криптографически проверяет первый изменяемый код в системе до его выполнения».

На STM32:

- **RTV = наш бутлоадер**: он проверяет заголовок образа приложения (magic, size), хеш (SHA-256) и подпись (ECDSA P-256). Только при успешной проверке выполняется переход в приложение.
- В [X-CUBE-SBSFU](https://www.st.com/en/embedded-software/x-cube-sbsfu.html) ту же роль играет Secure Boot из пакета; в [MCUboot](https://docs.mcuboot.com/) — bootutil при порте на STM32.

### 1.3 Chain of Trust (CoT) — цепочка доверия

**CoT** — последовательность компонентов, где каждый следующий **проверен** предыдущим. RoT — первое звено; как только управление передаётся непроверенному коду, цепочка обрывается.

В нашем случае:

1. **RoT/RTV** — бутлоадер по `0x08000000` (мы ему доверяем).  
2. Он проверяет образ по `0x08010000` (заголовок + подпись).  
3. При успехе передаёт управление по `entry_point` (например `0x08010080`) — **второе звено CoT**.  
4. Дальнейшие обновления (если появятся) могут продолжать цепочку: приложение проверяет следующий образ и т.д.

## 2. Verified Boot и Measured Boot (кратко)

- **Verified Boot** — проверка образа **до** запуска (подпись/хеш). Непроверенный код **не выполняется**. Наш бутлоадер реализует именно это.
- **Measured Boot** — **фиксация** того, что было запущено (например, логирование хешей в TPM или во Flash), без решения «запускать или нет». Для последующего аудита и аттестации.

На STM32 без TPM measured boot можно имитировать (например, писать хеш образа в отдельную область Flash или в NVRAM), но типичный сценарий для встраиваемых систем — **verified boot** (блокировать неподписанное/поддельное ПО). Подробнее сравнение — в [3mdeb/verified-boot](https://github.com/3mdeb/verified-boot/blob/master/verified_boot_main.md).

---

## 3. Целостность и подлинность

- **Целостность (integrity):** данные не менялись без разрешения. Обеспечивается **хешем** (у нас — SHA-256 по телу приложения). Изменение хотя бы байта меняет хеш.
- **Подлинность (authenticity):** уверенность в источнике данных. Обеспечивается **подписью** (у нас — ECDSA P-256 по хешу). Только владелец закрытого ключа мог создать подпись; открытый ключ в бутлоадере проверяет её.

Один только хеш не гарантирует источник (враг может подменить и образ, и хеш). Одна только подпись без привязки к хешу не привязана к содержимому. Поэтому в нашем формате: **сначала считали хеш образа, потом проверили подпись от этого хеша** — получаем и целостность, и подлинность (и неотказуемость, non-repudiation).

Формат заголовка в проекте: [common/image_header.h](../common/image_header.h) — magic, version, image_size, entry_point, reserved, signature[64].

## 4. Где мы в этой схеме

| Элемент | В этом проекте (stm32_secure_boot) |
|--------|-----------------------------------|
| RoT    | Бутлоадер по 0x08000000 (первый код из Flash при Boot0=0) |
| RTV    | Тот же бутлоадер: проверка заголовка, SHA-256, ECDSA перед jump |
| CoT    | Bootloader → (проверка) → Application |
| Verified boot | Да: неподписанный/неверный образ не запускается |
| Measured boot | Нет (при желании можно добавить запись хеша в Flash) |
| Целостность | SHA-256 по телу приложения |
| Подлинность | ECDSA P-256, публичный ключ в бутлоадере (keys.h) |

Сборка и прошивка: [docs/BUILD_RU.md](BUILD_RU.md). Официальные и похожие решения: [docs/REFERENCES_RU.md](REFERENCES_RU.md).

## 5. Минимальные требования к «правильному» Verified Boot на STM32

(Идеи, общие для нашего подхода, X-CUBE-SBSFU и MCUboot.)

- **RoT/RTV в защищённой области**  
  Код бутлоадера не должен подменяться. На практике: запись только через доверенный канал; при необходимости — включить Write Protection (WRP) на сектор(ы) с бутлоадером (см. Reference Manual конкретной серии).

- **Проверка до выполнения**  
  Ни одного байта кода приложения не выполнять до успешной проверки подписи (и при необходимости — версии, размера).

- **Минимальный TCB**  
  В доверенную вычислительную базу входят только: бутлоадер, криптобиблиотека (или аппаратный блок), хранилище публичного ключа. Чем меньше кода в TCB, тем проще аудит и меньше поверхность атаки.

- **Ключи**  
  Закрытый ключ — только на стороне сборки/CI; в устройстве только публичный ключ (или хеш публичного ключа). Не хранить закрытый ключ во Flash МК.

- **Воспроизводимость**  
  Образ приложения должен быть детерминированно подписываться (одни и те же входные данные → одна и та же подпись), чтобы можно было верифицировать сборку.

## 6. Угрозы и ограничения (кратко)

- **Подмена бутлоадера:** без WRP злоумышленник с доступом к программированию Flash может записать свой код по 0x08000000. Мера: WRP, контроль доступа к программатору, безопасная прошивка на производстве.
- **Утечка закрытого ключа:** кто угодно сможет подписывать образы. Мера: ключ только на безопасном сервере сборки, не в прошивке и не в репозитории в открытом виде.
- **Откат версии (downgrade):** текущий минимальный бутлоадер не проверяет версию строго (поле version в заголовке есть, но политика «не запускать старую версию» не реализована). При необходимости — добавить проверку version против минимально допустимой, хранящейся в бутлоадере или в Option Bytes.

Подробные модели угроз для Verified Boot в целом см. в [3mdeb/verified-boot (threat-model)](https://github.com/3mdeb/verified-boot/blob/master/threat-model.md).

## 7. Привязка к экземпляру устройства (MB/карте)

**Привязка к экземпляру** — ограничение запуска прошивки только на конкретной плате/микроконтроллере (по уникальному идентификатору или ключу). Нужна, чтобы образ, снятый с одной платы, нельзя было запустить на другой, или чтобы лицензировать прошивку «под одну карту».

### 7.1 Уникальный ID микроконтроллера (UID)

У STM32 в кристалле прошит **96-битный Unique Device ID** (только чтение, изменить нельзя). Адрес в RM0433 для STM32H743/753/750:

- **UID base:** `0x1FF1E800`
- **3 слова по 32 бита:** UID[0], UID[1], UID[2] — всего 96 бит.

Чтение в коде бутлоадера (без HAL):

```c
#define UID_BASE  0x1FF1E800UL
#define UID0      (*(const volatile uint32_t *)(UID_BASE + 0x00))
#define UID1      (*(const volatile uint32_t *)(UID_BASE + 0x04))
#define UID2      (*(const volatile uint32_t *)(UID_BASE + 0x08))
```

Дополнительно STM32H7 имеет **Device ID** (идентификатор типа кристалла) по адресу `0x1FF1E7E0` (2 байта). UID различает экземпляры одного и того же типа.

### 7.2 Способы привязки

| Подход | Суть | Плюсы | Минусы |
|-------|------|--------|--------|
| **UID в подписываемых данных** | При подписании образа в «подписываемый» блок входят magic, size, version и **хеш UID** (или сам UID). Подпись = Sign(SHA256(image \|\| UID_hash)). Бутлоадер читает UID, считает UID_hash, собирает тот же блок, проверяет подпись. | Жёсткая привязка к одной плате. | Для каждой платы свой образ (или нужно подписывать на устройстве/на производстве по списку UID). |
| **Опциональное поле в заголовке** | В `reserved[]` или новое поле в `image_header_t`: например `uint8_t uid_hash[32]` (SHA-256 от UID). Если поле нулевое — проверку UID не делаем (как сейчас). Если не нулевое — бутлоадер сравнивает SHA256(UID) с этим полем. | Один образ можно раздать всем, а привязку включить только там, где нужно (подписывать образ с подставленным UID_hash для конкретной платы). | Нужно на производстве/у заказчика генерировать образ под конкретный UID или хранить таблицу UID→образ. |
| **Ключ, уникальный для устройства** | На каждой плате свой ключ (в OTP, eFuse или внешнем secure element, например STSAFE-A110). Образ шифруется или подписывается под этот ключ. Бутлоадер проверяет подпись ключом этого устройства. | Максимальная привязка, защита от копирования образа. | Сложнее инфраструктура: генерация/инъекция ключей на производстве, возможно отдельный чип. |
| **UID как «соль» при проверке** | Подпись остаётся одна (без UID), но бутлоадер перед проверкой подписи добавляет UID в логику (например, считает hash(image \|\| UID) и проверяет подпись от этого хеша). Тогда образ, подписанный без учёта UID, не пройдёт на другом устройстве. | Не нужно хранить на сервере список UID. | Закрытый ключ должен использоваться в среде, где известен UID (прошивка на производстве), или схема усложняется (например, производственный сервис подписывает по запросу с UID). |

В **текущем проекте** привязки к UID нет: один и тот же `signed_app.bin` может быть прошит на любую плату с тем же типом МК. Добавление привязки — расширение формата заголовка и логики подписи/проверки (см. ниже).

### 7.3 Куда вписать UID в нашем формате

- **Вариант A:** использовать поле **reserved[16]** в [image_header.h](../common/image_header.h): например первые 12 байт = UID (96 бит), или 32 байта = SHA-256(UID). Бутлоадер после проверки подписи (как сейчас) дополнительно проверяет: если reserved не нули — читает UID и сравнивает с reserved (или сравнивает SHA256(UID) с reserved).
- **Вариант B:** расширить заголовок: добавить поле `uint8_t uid_binding[32]` (SHA-256 от UID целевого устройства). При сборке образа для конкретной платы скрипт подписи запрашивает UID (или читает из файла), считает SHA256(UID), пишет в uid_binding, подписывает весь заголовок вместе с телом. Бутлоадер читает UID, считает SHA256(UID), сравнивает с uid_binding; при несовпадении отказывает в запуске.

В обоих вариантах **подпись должна охватывать** и поле с UID/uid_binding, иначе можно подменить UID в заголовке без смены подписи.

### 7.4 Официальные решения ST

- **X-CUBE-SBSFU:** поддержка внешнего secure element (STSAFE-A110) для хранения ключей и, при необходимости, привязки к устройству.
- **SFI (Secure Firmware Install):** на поддерживаемых сериях (H5, H7RS, L5, U5 и др.) — безопасная установка образа с привязкой к устройству на этапе производства (ключи/секреты в HSM, образ ставится только в «своё» устройство).
- **Option Bytes / OTP:** на части STM32 есть OTP-области или option bytes для хранения device-specific данных; их можно использовать под хранение хеша UID или ключа (в зависимости от серии и политики безопасности).

Итог: привязка к MB/карте реализуется через **UID** (чтение по `0x1FF1E800`) и/или **уникальный ключ на устройстве**; в нашем минимальном бутлоадере её пока нет, но расширение заголовка и скрипта подписи по вариантам выше её добавляет.
